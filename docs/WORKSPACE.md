# Stockwell workspace and offline operation

Run on Node 24+ with PostgreSQL, using Neon's pooled DATABASE_URL in Vercel. Set BETTER_AUTH_SECRET and BETTER_AUTH_URL, then run `pnpm db:migrate` before deployment. Better Auth manages users, password hashes and 7-day sessions in the shared database. New instances and deployments do not depend on local files. HTTPS sessions use Secure, HttpOnly, SameSite=Strict cookies. Write endpoints require the exact configured Origin. Authentication attempts are rate limited by account email in Postgres. Database session validation keeps sign-out and expiration authoritative across instances. See [setup, deployment and legacy SQLite import](../README.md).

Sign up creates an owner workspace. Owners use Settings to change store name, choose an optional PNG/JPEG/WebP image up to 500 KB, and create email-bound invitations valid for seven days. Share the generated link with the intended member. New members sign up from the invitation; owners can change assigned modules. Owners cannot remove their own authority. Existing accounts cannot join a second workspace in this implementation. Assigned modules grant navigation and server-enforced write authority; the retail dataset is shared with workspace members for cross-module stock, contact and billing calculations. This is not row-level data isolation.

The owner can import previous stockwell.retail.v1 browser records into an empty workspace from Settings. The original browser copy is retained.

After a successful online sign-in, the workspace is cached on this device. Each edit persists its UUID, actor session context, action time, module, and resulting records before it appears saved. The service worker caches the app shell and observed static assets. Previously loaded workspaces can open and edit during internet or server interruption. First sign-in/sign-up, invitations and owner permission/profile changes require the server. Fonts not yet downloaded may require online access; browser print remains available. Device cache should be used only on trusted devices.

The queue retries every 15 seconds while the tab is visible, on reconnect, and when the tab becomes visible again. Server changes are committed transactionally, once per event ID. Server revisions prevent lost updates: concurrent changes block the queue with an explicit conflict. Export pending changes to JSON before loading current server records; loading server records discards the pending local queue after confirmation. No automatic merge of financial records. Permission revocation and expired sessions preserve the queue for resolution. Signing in again preserves queued changes for that workspace. Sign-out requires a fully synced queue, revokes the server session, and clears that workspace's local cache. Closing a browser leaves pending edits cached.

Every accepted record change and owner settings change creates an audit event recording actor name/email, module, action, changed record IDs and fields, client action time and server receipt time. Owner notifications and logs update during sync/polling, with a New indicator and read acknowledgement. The UI shows the latest 300 events; the server retains full history. Offline changes notify the owner only after they reach the server.

Set RESEND_API_KEY and RESEND_FROM (a Resend-verified sender) in .env.local or deployment secrets. Recipients are the workspace owner's registered email. Keys never enter client bundles. Resend sends plain-text record-change summaries with an idempotency key. Accepted-by-provider messages show sent (not a delivery receipt). Failures remain in a persistent outbox with exponential retries. On Vercel, authenticated API activity and Settings drain due retries. A database lease prevents separate instances from claiming the same due batch simultaneously. Email remains queued when no API requests are running; delivery resumes with subsequent activity. A persistent Node deployment can still drain the outbox every 30 seconds. Scheduling independent delivery is optional and can increase database compute usage. Resend idempotency retention is 24 hours; ambiguous failures beyond that window can cause duplicate emails. Actual email delivery requires configured credentials and a verified domain; this environment did not send real emails.
