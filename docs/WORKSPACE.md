# Stockwell workspace and offline operation

Run on Node 24+ with a persistent disk (single server instance). SQLite stores accounts, salted scrypt password hashes, hashed 7-day session tokens, workspace records, invitations, audit history and email outbox in STOCKWELL_DATA_DIR (default .stockwell). Back up that directory. This is not a stateless/serverless database adapter. Use HTTPS in deployment; HTTPS sessions use Secure, HttpOnly, SameSite=Strict cookies. Write endpoints require matching Origin. Authentication attempts are rate limited by account email.

Sign up creates an owner workspace. Owners use Settings to change store name, choose an optional PNG/JPEG/WebP image up to 500 KB, and create email-bound invitations valid for seven days. Share the generated link with the intended member. New members sign up from the invitation; owners can change assigned modules. Owners cannot remove their own authority. Existing accounts cannot join a second workspace in this implementation. Assigned modules grant navigation and server-enforced write authority; the retail dataset is shared with workspace members for cross-module stock, contact and billing calculations. This is not row-level data isolation.

The owner can import previous stockwell.retail.v1 browser records into an empty workspace from Settings. The original browser copy is retained.

After a successful online sign-in, the workspace is cached on this device. Each edit persists its UUID, actor session context, action time, module, and resulting records before it appears saved. The service worker caches the app shell and observed static assets. Previously loaded workspaces can open and edit during internet or server interruption. First sign-in/sign-up, invitations and owner permission/profile changes require the server. Fonts not yet downloaded may require online access; browser print remains available. Device cache should be used only on trusted devices.

The queue retries every 15 seconds and on reconnect. Server changes are committed transactionally, once per event ID. Server revisions prevent lost updates: concurrent changes block the queue with an explicit conflict. Export pending changes to JSON before loading current server records; loading server records discards the pending local queue after confirmation. No automatic merge of financial records. Permission revocation and expired sessions preserve the queue for resolution. Signing in again preserves queued changes for that workspace. Sign-out requires a fully synced queue, revokes the server session, and clears that workspace's local cache. Closing a browser leaves pending edits cached.

Every accepted record change and owner settings change creates an audit event recording actor name/email, module, action, changed record IDs and fields, client action time and server receipt time. Owner notifications and logs update during sync/polling, with a New indicator and read acknowledgement. The UI shows the latest 300 events; the server retains full history. Offline changes notify the owner only after they reach the server.

Set RESEND_API_KEY and RESEND_FROM (a Resend-verified sender) in .env.local or deployment secrets. Recipients are the workspace owner's registered email. Keys never enter client bundles. Resend sends plain-text record-change summaries with an idempotency key. Accepted-by-provider messages show sent (not a delivery receipt). Failures remain in a persistent outbox with exponential retries. The persistent Node server drains due outbox messages every 30 seconds, including while clients are closed; API activity and Settings also trigger due retries. Delivery pauses while the server is stopped and resumes after restart. Resend idempotency retention is 24 hours; ambiguous failures beyond that window can cause duplicate emails. Actual email delivery requires configured credentials and a verified domain; this environment did not send real emails.
